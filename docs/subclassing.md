# Subclassing C++ classes from Zig in cpp-bindgen

**Status:** implemented in cpp-bindgen c50ad89. `cpp_virtuals`,
`cpp.Subclass` and `cpp_overrides` landed as proposed. The proposal's
`cpp.vcall` is `cpp.bindVirtual`, and the runtime check is `cpp.verifyVtable`
plus the check in `Subclass.init`. openFrameworks-zig uses it for
`ofBaseApp`, and `src/cpp/ofzig_app.cpp` is gone. cpp-bindgen 60a12f1 added
member access (`.access = .protected`), which the node classes need, so
`ofNode`, the cameras, `ofLight` and the primitives can be extended too.

A feature proposal, written from the openFrameworks side, and the sequel to
[inheritance.md](inheritance.md). That document made a derived C++ class
*bindable*. This one makes a C++ class *extendable*: a Zig type that C++ code
holds as a base pointer and calls through its virtual functions.

The constraint is the one cpp-bindgen already lives by. The C++ glue is
optional. It checks layouts and makes header-only definitions exist, and
nothing a binding *does* may depend on it. Subclassing must work the same way:
no hand-written C++, and no generated C++ shim either.

Every layout claim below was measured with the toolchain this project uses
(`zig cc`, clang, `-fdump-vtable-layouts`) on both ABIs:
`x86_64-windows-msvc` for MSVC and `x86_64-windows-gnu` for Itanium. The
mechanism was prototyped, and the prototype passed on both ABIs, in Debug and
ReleaseFast. It was removed once the feature landed: cpp-bindgen's own tests
(`src/vtable.zig`, `src/subclass.zig`, `test/vtable_fixture.cpp`) now cover
everything it showed, and `test/vtables.zig` here checks the oF classes.

## Why

`src/cpp/ofzig_app.cpp` is the only hand-written C++ in this package, and it
exists for one class. oF drives an app through `ofBaseApp`'s virtual
functions, so the package compiles a C++ subclass whose overrides forward to a
struct of C function pointers. `src/app.zig` mirrors that struct field by
field, and a runtime size comparison is the only thing keeping the two in
step.

The same need appears all over oF, and today none of it can be met:

| class | virtual a sketch wants to override |
|---|---|
| `ofNode` | `customDraw`, `onPositionChanged`, `onOrientationChanged`, `onScaleChanged` |
| `ofCamera` | `begin(const ofRectangle&)` |
| `ofBaseMaterial` | `begin`, `end`, `getDiffuseColor` and the other getters |
| `ofBaseSoundOutput` / `ofBaseSoundInput` | `audioOut`, `audioIn` |
| `ofThread` | `threadedFunction` |

A shim per class does not scale, and a shim generated by the glue would make
the glue mandatory. So the question is whether Zig can do what a C++ compiler
does for a derived class, by itself.

## A subclass is data plus calls

A C++ compiler does four things for `struct D : B { void f() override; }`:

1. **It emits a vtable.** An array of function pointers in read-only data,
   preceded by RTTI. Slots that `D` does not override hold `B`'s definitions.
2. **It constructs.** `D()` calls `B()`, which installs `B`'s vtable, and then
   stores `D`'s vtable pointer over it.
3. **It compiles the overrides.** On x86_64 a member function is the C calling
   convention with `this` first.
4. **It destroys.** The destructor slot runs `D`'s destructor body, calls
   `~B()`, which puts `B`'s vtable back before it runs, and frees the memory if
   the caller asked for that.

Zig can do every one of these. The vtable is a `const` array built at
comptime, and the relocations to `B`'s functions are the same ones C++ would
emit. Construction and destruction are calls to symbols cpp-bindgen already
binds. The overrides are `callconv(.c)` functions. What Zig lacks is the
*layout*: which slot is which. That is the whole of the feature, and it is
computable.

## What the layout is

### MSVC

A `struct ZigCam : ofCamera` with one override, dumped by clang on
`x86_64-windows-msvc`:

```
VFTable for 'ofNode' in 'ofCamera' in 'ZigCam' (11 entries).
   0 | ZigCam RTTI
   1 | ZigCam::~ZigCam() [vector deleting]
   2 | void ofNode::customDraw()
   3 | void ofNode::customDraw(const ofBaseRenderer *) const
   4 | void ofNode::draw() const
   5 | void ofNode::onPositionChanged()
   6 | void ofNode::onOrientationChanged()
   7 | void ofNode::onScaleChanged()
   8 | void ZigCam::begin(const ofRectangle &)
   9 | void ofCamera::begin()
  10 | void ofCamera::end()
```

The vtable pointer points at entry 1. Entry 0 is the RTTI "complete object
locator". The rules, all visible above:

- **Base slots come first.** A class's new virtuals are appended after the
  slots of its primary base.
- **Overloads are grouped and reversed.** `ofNode.h` declares
  `customDraw(const ofBaseRenderer*) const` before `customDraw()`, and the
  table holds them the other way round. `ofCamera.h` declares `begin()` before
  `begin(const ofRectangle&)`, and again the table reverses them. An overload
  set takes the position of its first declaration, and its members are laid
  out last to first.
- **The destructor is one slot.** It is the "vector deleting destructor",
  `void* (this, unsigned flags)`. Bit 0 of `flags` means "free the memory too".
  Bit 1 means array delete.

`ofBaseApp` is the hard case. It derives from `ofBaseSoundInput` and
`ofBaseSoundOutput`, both polymorphic, so an app object holds two vtable
pointers:

```
VFTable for 'ofBaseSoundInput' in 'ofBaseApp' in 'ZigApp' (48 entries).
   0 | ZigApp RTTI
   1 | ZigApp::~ZigApp() [vector deleting]
   2 | void ofBaseSoundInput::audioIn(float *, int, int)
   ...
   6 | void ofBaseApp::setup(ofEventArgs &)
   7 | void ofBaseApp::setup()
   ...
VFTable for 'ofBaseSoundOutput' in 'ofBaseApp' in 'ZigApp' (6 entries).
   0 | ZigApp RTTI
   1 | ZigApp::~ZigApp() [vector deleting]
       [this adjustment: -8 non-virtual]
   2 | void ofBaseSoundOutput::audioOut(float *, int, int)
   ...
```

- **Each polymorphic base keeps its own table**, at the offset where that base
  sits. inheritance.md's calculator already knows the offsets.
- **New virtuals go to the primary table**, the one at offset 0. All of
  `ofBaseApp`'s own virtuals are in the first table.
- **An override replaces its slot in every table that has it.** The destructor
  appears in both tables. The second one is entered with `this` pointing at
  the `ofBaseSoundOutput` subobject, eight bytes in, and has to find the whole
  object.
- **Every table carries RTTI.** Each has its own locator, and the locators
  record the table's offset.

### Itanium

The prototype's fixture, which has the same shape as `ofNode`/`ofCamera` and
`ofBaseApp`, dumped on `x86_64-windows-gnu`:

```
Vtable for 'Cam' (11 entries).
   0 | offset_to_top (0)
   1 | Cam RTTI
   2 | Cam::~Cam() [complete]
   3 | Cam::~Cam() [deleting]
   4 | int Node::customDraw(int) const
   5 | int Node::customDraw()
   6 | int Node::draw() const
   7 | int Node::onChanged()
   8 | int Cam::begin()
   9 | int Cam::begin(int)
  10 | int Cam::end()

Vtable for 'App' (11 entries).
   0 | offset_to_top (0)
   1 | App RTTI
   2 | App::~App() [complete]
   3 | App::~App() [deleting]
   4 | int In::audioIn(int)
   5 | int App::update()
   6 | offset_to_top (-8)
   7 | App RTTI
   8 | App::~App() [complete]
       [this adjustment: -8 non-virtual] method: Out::~Out()
   9 | App::~App() [deleting]
       [this adjustment: -8 non-virtual] method: Out::~Out()
  10 | int Out::audioOut(int)
```

- **Declaration order**, with no grouping or reversal.
- **Two destructor slots**, complete then deleting, each `void (this)`.
- **A two-word prefix**: offset to top, then a pointer to the `typeinfo`.
- **The same structure otherwise**: base slots first, new virtuals in the
  primary table, one table per polymorphic base. Itanium happens to place the
  tables of one class next to each other in a single symbol, but a vtable
  pointer is only ever followed forward from where it points, so separate
  arrays are equivalent.

### The Zig class is always a leaf

C++ never names the Zig type. It only ever holds a pointer to one of the C++
bases. So the only tables that have to exist are the ones those bases'
callers read, and the Zig subclass never needs a slot of its own. This
removes the parts of the ABI that would otherwise be hard. Itanium adds
primary-table entries for a derived class's overrides of secondary-base
functions, and both ABIs give a derived class's new virtuals new slots.
Nothing ever calls either through the Zig type, because nothing has its
static type.

### Every symbol already exists

The vtable references four kinds of symbol. All of them are external:

| what | MSVC | Itanium |
|---|---|---|
| a base's virtual definition | `?draw@ofBaseApp@@UEAAXXZ` | `_ZN9ofBaseApp4drawEv` |
| the base constructor and destructor | `??0ofBaseApp@@QEAA@XZ`, `??1ofBaseApp@@UEAA@XZ` | `C2`, `D2` |
| RTTI | `??_R4ofBaseApp@@6BofBaseSoundInput@@@` (one per table) | `_ZTI9ofBaseApp` |

The IR for `ofBaseApp.cpp` shows the definitions as ordinary external
functions and the locators as `linkonce_odr`, which is a COMDAT with an
external name. cpp-bindgen already binds the first two kinds. RTTI needs two
new manglings: `??_R4<class>@@6B<base path>@` and `_ZTI<class>`. MSVC uses
`6B@` when the class has only one table.

A header-inline virtual, such as `ofCamera::begin()` or
`ofNode::onPositionChanged()`, exists as a symbol only because some
translation unit emitted the base's vtable. Any TU that defines an
out-of-line constructor emits the vtable, so in practice these always exist,
and the prototype links one this way. Where the glue is present, its forced
definitions make it certain. That is the glue's existing job, and the feature
does not depend on it.

## Proposed API

### Binding side: `cpp_virtuals`

Each polymorphic class lists the virtual functions it declares, in header
order, including the destructor and including overrides. It does not list
inherited ones:

```zig
// node.zig
pub const Node = extern struct {
    // ...as today...
    pub const cpp_virtuals: []const Signature = &.{
        dtor_sig,
        customDraw_renderer_sig,   // customDraw(const ofBaseRenderer*) const
        customDraw_sig,            // customDraw()
        draw_sig,
        onPositionChanged_sig,
        onOrientationChanged_sig,
        onScaleChanged_sig,
    };
};

// camera.zig
pub const Camera = extern struct {
    // ...as today...
    pub const cpp_virtuals: []const Signature = &.{ dtor_sig, begin_sig, begin_viewport_sig, end_sig };
};
```

Header order is what a binding author can read off the file, and it is the
same on both ABIs. cpp-bindgen derives the slot order. An author never thinks
about MSVC's reversal, and a binding written for one ABI is correct for the
other.

Each class lists its own virtuals because only it knows them. An entry that
matches a base's slot by name, parameters and constness is an override and
takes that slot. Any other entry is a new slot. The list has to be complete.
A missing entry shifts every later slot, which is why the runtime check below
exists.

### Subclass side: `cpp.Subclass`

A Zig subclass is an ordinary Zig struct with the C++ object as a field:

```zig
const OrbitCam = struct {
    cpp: cpp.Subclass(of.Camera, OrbitCam, "cpp"),
    angle: f32 = 0,
    radius: f32 = 300,
    trail: std.ArrayList(of.Vec3) = .empty,

    pub const cpp_overrides = .{
        .{ of.Camera.begin_viewport_sig, beginViewport },
        .{ of.Node.onPositionChanged_sig, positionChanged },
    };

    fn beginViewport(self: *OrbitCam, viewport: *const of.OfRectangle) void {
        self.angle += of.getLastFrameTime();
        const node = self.cpp.base.node();
        node.setPosition(.{ @cos(self.angle) * self.radius, 100, @sin(self.angle) * self.radius });
        node.lookAt(.{ 0, 0, 0 });
        // "super" is the direct call bindings already make
        cpp.bind(of.Camera.begin_viewport_sig)(&self.cpp.base, viewport);
    }

    fn positionChanged(self: *OrbitCam) void {
        self.trail.append(gpa, self.cpp.base.node().getPosition()) catch {};
    }

    /// Optional. Runs before ~ofCamera(), as a C++ destructor body would.
    pub fn cpp_destroy(self: *OrbitCam) void {
        self.trail.deinit(gpa);
    }
};
```

```zig
self.orbit = .{ .cpp = undefined };
self.orbit.cpp.init();         // ofCamera(), then OrbitCam's vtable
defer self.orbit.cpp.deinit(); // cpp_destroy, then ~ofCamera()

self.orbit.cpp.base.begin();   // ofCamera::begin() calls begin(viewport) virtually: beginViewport runs
of.drawGrid(50, 4, .{ .y = true, .x = false, .z = false });
self.orbit.cpp.base.end();
```

- **`cpp.Subclass(Base, Outer, field)`** is an `extern struct { base: Base }`.
  It has exactly `Base`'s size and layout, so C++ sees a real `Base`. `Outer`
  is free to be any Zig struct. It need not be `extern`, and its other fields
  can be slices, allocators, or anything else. An override reaches it from the
  C++ `this` with `@fieldParentPtr`. The prototype confirms that a field whose
  type is generated from its own containing struct compiles, because the
  field's layout depends only on `Base`.
- **`cpp_overrides`** pairs each override with the Signature it overrides. It
  is a list of pairs rather than a naming convention because C++ overloads
  virtuals and Zig has no overloading: `customDraw` and `begin` each have two.
  The Signature can come from any class in the chain.
- **`cpp_destroy`** is the destructor body. **`cpp_free`** releases the memory
  when C++ deletes the object. Without `cpp_free`, a `delete` from C++ is a
  panic naming the type, because Zig owns the storage and C++ cannot know how
  it was allocated.
- **`init`** runs the base constructor and then installs the vtables. A
  variant takes a constructor Signature and arguments for a base with no
  default constructor. **`deinit`** runs `cpp_destroy` and then the base
  destructor directly.

### Virtual calls from Zig: `cpp.vcall`

Once slot indices exist, a virtual call needs no C++ either. It loads the
pointer from the vtable and calls it:

```zig
cpp.vcall(of.Camera.begin_viewport_sig, &cam.base, .{&viewport});
```

This also fixes a trap in the bindings as they stand. `.virtual = true`
changes only the MSVC mangling, and the bound call is a direct call to that
class's implementation. Today, `Camera.begin` called on an `OrbitCam` would
run `ofCamera::begin` and skip the override. The oF wrappers for virtual
methods (`Camera.begin`, `Material.begin`, `Mesh.enableNormals` and the rest)
should move to `vcall`. That costs one indirect jump and behaves the way the
same C++ call would.

## How cpp-bindgen would implement it

**Slot layout.** `tables(C)` is the list of `C`'s vtables. Each entry holds
an offset, the base that introduced that vtable pointer (MSVC names RTTI after
it), and the slots. Each slot records its kind (method, complete destructor,
deleting destructor), the Signature as first declared, and the *owner*: the
class whose definition is the final overrider. The table list is built
recursively:

1. Collect every polymorphic base's tables, shifted by that base's offset from
   `baseOffset`. The first polymorphic base is the primary one, at offset 0.
   With no polymorphic base, start one empty table at offset 0.
2. For each Signature in `C.cpp_virtuals`, replace the owner of every slot it
   overrides, in every table. Collect the rest.
3. Append the rest to the primary table in ABI order. MSVC groups by name at
   the first declaration and reverses each group, with one destructor slot.
   Itanium keeps declaration order, with two destructor slots.

This is pure comptime work. It is tested against the dumps above for single
inheritance, two-level chains, and two polymorphic bases.

**The tables.** For each of the base's tables, `Subclass` emits a `const`
array: the prefix, then one word per slot. The MSVC prefix is the RTTI
locator. The Itanium prefix is the negated offset and the `typeinfo`. A slot
holds one of three things. An overridden method gets a generated adapter. The
destructor slots get generated destructors. Anything else gets the owner's
definition, the same `@extern` `cpp.bind` uses. The arrays live in read-only
data with relocations, exactly as C++ would emit them.

**Adapters.** One per overridden slot per table. An adapter receives the C++
`this`, which is the subobject that table belongs to. It subtracts that
table's offset, recovers `Outer` with `@fieldParentPtr`, and calls the Zig
method. Its parameter list is the inverse of the call-side `Plan` cpp-bindgen
already has: the same references-as-pointers, and the same hidden return
pointer on the same side of `this`. The callee side has one asymmetry, noted
under limits. Arity is handled the way `trampoline` already handles it: one
entry point per parameter count.

**Destructors.** An MSVC deleting destructor runs `cpp_destroy` and the base
destructor, calls `cpp_free` if bit 0 of the flags is set, and returns
`this`. Itanium's complete destructor does the first half. Its deleting
destructor does both halves. The second table of a multiply-inherited base
gets its own copies, with their own offset, so `delete` through
`ofBaseSoundOutput*` finds the whole object.

**RTTI.** The base's own. `dynamic_cast` to the base and to anything above it
works, and so does `dynamic_cast<void*>`, because the locators and the
offset-to-top words record each table's real offset. `typeid` names the base.
That is the only thing a Zig type could truthfully be called from C++, and
nothing in oF asks for more.

**The runtime check.** `init` in a safe build reads the vtables the base
constructor has just installed, before replacing them. Every method slot must
hold exactly the definition the computed layout predicts. A misordered or
incomplete `cpp_virtuals` moves later slots, so it fails here, at the first
construction, naming the slot:

```
[default] (warn): proto.BadNode: slot 1 of the table at 0 is not Node::customDraw
```

That line is the prototype's output for a binding whose two `customDraw`
overloads are listed the wrong way round.

**Compile-time checks.** Every `cpp_overrides` Signature must match a method
slot of the base. Every override's parameter types must be the adapter's.
Virtual bases are refused, as they already are for layout. A method in
`cpp_virtuals` without `.virtual = true` is refused, since it would mangle to
the wrong symbol on MSVC. The destructor is the exception: it takes its
virtualness from `cpp_virtual_dtor`, as it does today.

## Prototype results

The prototype was `vt.zig`, the feature as a library on top of cpp-bindgen
3ea6442 with no changes to cpp-bindgen, plus `fixture.cpp`, `proto.zig` and
`build.zig`. It has since been removed; this section records what it showed. The fixture is plain C++ that
knows nothing about Zig. `Node`/`Cam` stand in for `ofNode`/`ofCamera`, with
overloaded virtuals, a header-inline virtual, and a const virtual that calls a
non-const one. `In`/`Out`/`App` stand in for the sound bases and `ofBaseApp`.
Every behavior is driven from the C++ side, through base pointers. Each test
passes on both ABIs, in Debug and ReleaseFast:

| test | what it shows |
|---|---|
| computed slot layout matches clang's dump | slot order, owners and table offsets, per ABI |
| C++ reaches the Zig overrides, and the base's defaults stay | `Cam::begin()` calling `begin(int)` virtually lands in Zig. A super call reaches the base. A const path reaches a non-const override. A non-overridden header-inline virtual keeps its definition. `vcall` from Zig dispatches. `deinit` runs `cpp_destroy` and both C++ destructors. |
| RTTI is the base's | `dynamic_cast<Cam*>` succeeds and `typeid` names `Cam` |
| C++ deletes a heap Zig object through its base | the deleting destructor runs the chain and `cpp_free`, and the testing allocator reports no leak |
| two vtables | an override in the secondary table receives the adjusted `this`. `dynamic_cast<void*>` from the secondary base finds the whole object. `delete` through the secondary base runs all three C++ destructors and frees. |
| the debug check catches a misordered `cpp_virtuals` | `verify` returns `error.VtableMismatch` on both ABIs |

The prototype's own limits are listed at the top of `vt.zig`. It handles
identity call shapes only, unqualified class names, at most three arguments,
and no pure virtuals. None of these is a limit of the design. Each one is
covered below.

## Limits and open work

- **Non-identity call shapes.** An adapter must accept what the caller sends.
  That is the call-side `Plan` read in reverse, with a hidden return pointer
  for a class returned by value: `ofMaterial::getDiffuseColor` returns
  `ofFloatColor`, and MSVC returns every class from a member function that
  way. There is one asymmetry. On MSVC the *callee* destroys a by-value
  `managed_copy` argument, which is why `Plan.destroy` is Itanium-only today.
  An MSVC adapter therefore runs the argument's destructor after the Zig
  method returns. `ofBaseApp::dragEvent(ofDragInfo)` and
  `gotMessage(ofMessage)` are by-value overrides of exactly this kind.
- **Pure virtuals.** These need a marker on the Signature. The slot then holds
  `_purecall` or `__cxa_pure_virtual`, and a `Subclass` that leaves one
  unoverridden is a compile error, as instantiating an abstract class is in
  C++.
- **Nested multiple inheritance.** MSVC names a table after the *path* of
  bases that introduced it. The prototype handles one level, which covers
  `ofBaseApp`.
- **Out of scope:** virtual bases (vbtables and vtordisp), covariant returns,
  and array `delete[]` of a Zig object. All are refused, and none appears in
  the oF classes above.
- **Identical code folding.** The runtime check compares addresses. A release
  link with ICF can merge identical function bodies, and `ofBaseApp` has
  dozens of empty `{}` virtuals. So the check runs in safe builds only, where
  it is reliable.
- **Construction and destruction semantics are C++'s.** A virtual call from
  inside the base constructor or destructor reaches the base. Objects that
  register their address, such as `ofNode` with its parent and children,
  still cannot move. The vtable itself is static, so a class that does not
  register can move freely.
- **Exceptions.** A C++ exception that unwinds through a Zig override skips
  Zig `defer`s. This is unchanged from today's trampoline, and oF does not
  throw through its callbacks.
- **Other targets.** Linux and macOS use the same Itanium rules with a
  different C++ runtime. The vtable and `typeinfo` symbols are the same, but
  the prototype has not run there. AArch64 is not considered, matching
  cpp-bindgen's existing refusal of hidden return pointers there.

## What it changes in openFrameworks-zig

- **`src/cpp/ofzig_app.cpp` goes away.** `of.run` becomes a `cpp.Subclass` of
  `BaseApp` built from the app type's methods, using the same comptime
  detection as today, mapped onto `cpp_overrides` for the `ofEventArgs&`
  overloads. `ofRunApp` deletes its app, so the wrapper declares a `cpp_free`
  that does nothing, because the app lives in a Zig variable. The package
  then has no hand-written C++.
- **`ofBaseApp`'s binding grows a full `cpp_virtuals`**, and so does each
  sound base. The debug check would verify all of their slots, 48 in the
  first table and 6 in the second, on the first run.
- **`Node`, `Camera`, `EasyCam`, `Light`, `Material` and the primitives** list
  their virtuals and become extendable. A sketch can write the `OrbitCam`
  above, or a node with its own `customDraw`.
- **Virtual-method wrappers switch to `vcall`**, so calling a method on a Zig
  subclass from Zig behaves as it would from C++.

## Suggested order

1. **`cpp_virtuals` and `tables`.** Comptime only, tested against
   `-fdump-vtable-layouts` on both ABIs. The prototype's fixture and expected
   tables carry over.
2. **`vcall`.** It needs only step 1, and it fixes the dispatch trap in the
   existing bindings before anything is subclassed.
3. **`Subclass` for identity shapes**, with the RTTI manglings, the destructor
   slots and the runtime check. This is `vt.zig` moved into cpp-bindgen and
   generalized from three arguments to `trampoline`'s arity handling.
4. **Adapters for non-identity shapes**: the hidden return pointer, by-value
   classes, and MSVC's callee-destroy.
5. **Pure virtuals and nested MI naming.**
6. **openFrameworks-zig:** replace `ofzig_app.cpp`, then add `cpp_virtuals` to
   the 3D classes.
